### 1. `frontend/src/graph/Canvas.tsx:160` — the stop condition never fires; the asking never stops

**What is wrong.** `useNodesInitialized()` with its default options does **not** report handle bounds, and in this app it is permanently `false`. So `useHandlesTheLibraryHasMeasured` creates a 120 ms interval on mount and clears it only on unmount (or when the tile list changes, when it immediately makes another). The map forces a full re-measure of every tile ~8 times a second for the life of the page.

**How I know** (all read in the installed `@xyflow/react@12.11.6` / `@xyflow/system@0.0.82`, plus one probe I ran):

- `node_modules/@xyflow/react/dist/esm/index.mjs:4218-4221` — with the default `includeHiddenNodes: false` the selector returns `s.nodesInitialized` and never looks at `handleBounds`. (Only the `includeHiddenNodes: true` branch checks `internals.handleBounds`.)
- `node_modules/@xyflow/system/dist/esm/index.js:1671-1717` (`adoptUserNodes`) — `nodesInitialized` is computed from `internalNode.measured.width/height` alone, and a rebuilt internal node re-seeds `measured` from `userNode.measured`, which `toFlow` never sets (it sets `initialWidth`/`initialHeight`, `toFlow.ts:214`).
- `node_modules/@xyflow/react/dist/esm/index.mjs:3482-3499` — the store's `updateNodeInternals` ends in `set({})`; it never recomputes `nodesInitialized`. `setNodes` (`:3428-3457`) is the only writer, and `StoreUpdater` (`:281-320`) calls it only when the `nodes` **prop identity** changes — at which point `Canvas.tsx:245-266` has always built brand-new node objects, so `checkEquality` cannot preserve `measured`.
- `triggerNodeChanges` (`:3550`) only writes measurements back when `hasDefaultNodes` is true or `onNodesChange` is given; `Canvas.tsx:678-680` gives neither.

I ran a probe against the real `adoptUserNodes` (`/private/tmp/claude-501/-Users-kentgang-git3-katalyst/b70a1857-a894-4bbe-b3a6-4d7cf3ebc4f8/scratchpad/reviews/wire/probe.mjs`):

```
1. first setNodes (as Canvas builds them)          -&gt; nodesInitialized: false | handleBounds: undefined
2. next setNodes, new objects (hover/selection)    -&gt; nodesInitialized: false | handleBounds: undefined   (measurement discarded)
4. setNodes, same objects, after measurement       -&gt; nodesInitialized: true  | handleBounds: undefined   &lt;-- true WITHOUT handle bounds

Row 4 falsifies "false until every tile has handle bounds" outright. Row 2 shows why it can never turn true here.

**Cost, per tick, forever:** one `querySelector` per tile, then `getDimensions` + `getBoundingClientRect` on the tile and on each of its four sockets (`system:939` `getHandleBounds`), plus `getComputedStyle` on the viewport — roughly 5N forced layout reads for N tiles — and a new internal node object for every tile, which re-renders every `NodeWrapper`. **Smallest fix.** Ask for the fact that actually means "the sockets have been measured", and bound the asking:

```ts

const EVERY_TILE_MEASURED = { includeHiddenNodes: true } as const;

```ts
const drawing = useMemo(() =&gt; toFlow(world, heights, reserved), [world, heights, reserved]);
// Every box the glass holds, by identifier — the list the measuring asks
// about, held still so that the asking does not restart on every render.
// A map that is still being built puts a new box in this list each time a

### Do the three rules fight on a growing map?

The brief's question, answered from the library's source rather than from timing:

- **Does the hook re-run when a tile arrives?** Yes. `ids` is derived from `drawing.nodes`, which gains an entry per arrival, so the effect restarts and asks about the new box immediately.
- **Can it cause an observer loop?** No. `useUpdateNodeInternals` changes no box's size, so no `ResizeObserver` it does not own can re-fire; growth's own stage observer sets a state drawn by `.canvas::after`, absolutely positioned, taking no space. It also passes `triggerFitView: false`, so it cannot fight growth's `frameAgainOn`, and it does not remount a node, so it cannot take the keyboard away from #37's `mayLandAgain`.
- **Does it terminate? No — and that is a real finding about the fix branch, not about growth.** `useNodesInitialized()` with its default options returns the store flag, and that flag is set **only** by `adoptUserNodes`, which requires `userNode.measured.width/height` (`@xyflow/system` line 1706). This app passes controlled `nodes` with **no `onNodesChange`/`applyNodeChanges` and never sets `measured`** — `toFlow` sets `initialWidth`/`initialHeight`, which is #37's fix and which that particular check does not accept. So `nodesInitialized` is false from the first render and never becomes true, and `useHandlesTheLibraryHasMeasured` keeps a 120 ms interval alive for the life of the page, forcing a `getBoundingClientRect` over every tile and every handle about eight times a second. It still fixes the bug — by brute force — but its docstring's "the asking stops the moment the library says it has measured" is not true here, and a permanent forced-layout timer is exactly the kind of pressure that made the browser drop notifications in the first place (#37, and the measuring storm this branch already paid for once in `4c39fc8`).
  **The cheapest honest remedy is one argument:** `useNodesInitialized({ includeHiddenNodes: true })` reads the internal lookup instead (`handleBounds` set *and* `nodeHasDimensions`, which does accept `initialWidth`), so it flips true as soon as the library really has measured, and the asking stops. The branch has no `hidden` nodes, so the option's name is misleading but its effect is right. **I did not apply it: `fix/04-vanishing-wire` is read-only for me and is under its own review.**
- **Can the two be said as one rule?** Yes — *the library is never left with a box or a handle it has not measured.* #37 gives the library each box up front; the wire fix makes it go and look for the handles. They are one rule told in two places only because the app never feeds the library its own measurements back. Wire `onNodesChange` + `applyNodeChanges` (or carry `measured` on the nodes `toFlow` builds) and `nodesInitialized` starts meaning what it says, at which point both halves collapse into that one sentence. **Noted, not refactored** — it crosses the two branches.

## A′. The two pre-existing defects the coordinator asked about (not fixed, on main too)

Both reproduce **unchanged** on this branch, so the spread neither creates nor masks either.

**1. `observe(B=true)` leaves a cause at its prior (.3000 against Bayes's .4562).** Root cause: step 3 of `propagation.md` B5 — *keep the likelihood, not the coin flip*. `_one_pass` keeps `answer` (the claim's marginal likelihood in that draw) and throws away `came_true` (the realised flag). For a claim with **no causes** `total` is `broadcast(baseline)`, so `answer` is *identical in all eight worlds of a version*; `_per_version` then averages it over the surviving subset and gets exactly the same number back. Rao-Blackwellisation is exact for an *unconditional* mean, and invalid once you condition on another claim's realised outcome, because the conditioning event depends on the value that was discarded. The Bayes answer would come back by reading `came_true[A]` over the surviving worlds instead of `answer[A]`, at the cost of the variance reduction the whole band rests on — which is why this is a design decision and not a patch. It is the same phenomenon `diff.md` already records as G3's "moved only by reweighting", described there as a property rather than as a defect. **Interaction with the spread: none.** A has no incoming arrows, so no drawn push enters its baseline and its answer is still constant across worlds within a version. For a claim that *does* have causes, the answer already varies across worlds, the observation does reach it, and the spread only widens the band.

**2. `do(C)`/`do(R)` move B but move M1 and M2 by exactly 0.0000.** Root cause: `fired[claim_id] = came_true[:, :, starts]` where `starts = _point_of(points, setup.settled[claim_id])`. A **trigger** arrow multiplies its push by that single flag — the source's truth on the source's own *settled* day — while a **sustain** arrow multiplies by the full per-day `truth` array. `settled[B]` is day 2, the day B's *earliest* live arrow (`H→B`, lag 2) reaches it; `C→B` has lag 7 and `R→B` lag 5, so their pushes land in B's own series (B goes `.393 → .476` under `do(C)`) and are invisible to `B→M1` and `B→M2`. The intent in the code comment is defensible — a claim must be true-or-false once per world, or a sustaining push would flicker day to day — but the day chosen is a property of the map's *earliest* arrow rather than of when the trigger fires. The two readings that would let later pushes through are "the day this arrow's own push fires" (`settled[source] + lag`) and "the source's own resolve-by day"; both change every recorded number, so this is Kent's call. **Interaction with the spread: none that can change the zero.** The spread varies `H→B`, `C→B` and `R→B`, so it changes the distribution of B's day-2 flag — but identically in the base world and the `do(C)` world, because C's arrow contributes nothing on day 2 in either. The base-versus-branch difference stays exactly zero, which I confirmed by running the repro here.

## D. A diff row now says which half of *unchanged* failed

One field, one word, one rule.

```python
UnchangedBecause = Literal["under_the_floor", "versions_disagree"]
ClaimDiff.unchanged_because: UnchangedBecause | None     # required-but-nullable, like `agreement`
```

`_which_half_failed(state, move, agreement)` is the whole of it: nothing unless the state is `unchanged`; `under_the_floor` when `abs(move) &lt; MOVED_AT_LEAST`; otherwise `versions_disagree` when `agreement` is a number under `AGREEING_AT_LEAST`; otherwise nothing. **The floor is read first**, so a claim failing both halves says `under_the_floor` — and the two cases with no test to fail (a claim only one world holds; a claim no version counted in both numbers) carry nothing, because their absent `agreement` already says there was no direction. The reweighting case (G3) keeps `moved_only_by_reweighting` and also carries `versions_disagree`; `diff.md` says the fuller one is the one to show.

No default on the field, deliberately — a default would drop it out of the schema's `required` list, which is the exact trap item 3 of the plan is about.

Four tests, no typed-in words: `test_an_unchanged_claim_says_which_half_it_failed` (property test over generated maps; the expected word is worked out from the row's own two numbers), `test_only_an_unchanged_claim_says_which_half_it_failed`, `test_the_floor_is_read_first_when_a_claim_fails_both_halves`, `test_a_claim_moved_only_by_reweighting_keeps_both_fields`. ## A′. The two pre-existing defects the coordinator asked about — not fixed, reproduce on main too

**1. `observe(B=true)` leaves a cause at its prior (.3000 against Bayes's .4562).** Root cause is step 3 of `propagation.md` B5 — *keep the likelihood, not the coin flip*. `_one_pass` keeps `answer` (the marginal likelihood in that draw) and discards `came_true` (the realised flag). For a claim with **no causes**, `total` is `broadcast(baseline)`, so `answer` is **identical in all eight worlds of a version**; `_per_version` then averages it over the surviving subset and gets the same number back. Rao-Blackwellisation is exact for an *unconditional* mean and invalid once you condition on another claim's realised outcome, because the conditioning event depends on exactly the value that was discarded. The Bayes answer would come back by reading `came_true[A]` over the surviving worlds instead of `answer[A]`, at the cost of the variance reduction the whole band rests on — which is why it is a design decision, not a patch. It is the same phenomenon `diff.md` already records as G3's *moved only by reweighting*, described there as a property rather than a defect. **Interaction with the spread: none.** A has no incoming arrows, so no drawn push enters its baseline and its answer is still constant across worlds within a version. For a claim that *does* have causes, the answer already varies across worlds, the observation does reach it, and the spread only widens the band.

**2. `do(C)`/`do(R)` move B but move M1 and M2 by exactly 0.0000.** Root cause is `fired[claim_id] = came_true[:, :, starts]` where `starts = _point_of(points, setup.settled[claim_id])`. A **trigger** arrow multiplies its push by that single flag — the source's truth on the source's own *settled* day — while a **sustain** arrow multiplies by the full per-day `truth` array. `settled[B]` is day 2, the day B's *earliest* live arrow (`H→B`, lag 2) reaches it; `C→B` has lag 7 and `R→B` lag 5, so their pushes land in B's own series (B goes `.393 → .476` under `do(C)`) and are invisible to `B→M1` and `B→M2`. The intent in the code comment is defensible — a claim must be true-or-false once per world or a sustaining push would flicker — but the day chosen is a property of the map's *earliest* arrow rather than of when the trigger fires. The two readings that would let later pushes through are "the day this arrow's own push fires" (`settled[source] + lag`) and "the source's own resolve-by day"; both change every recorded number, so this is Kent's call. **Interaction with the spread: none that can change the zero.** The spread varies `H→B`, `C→B` and `R→B`, so it changes the distribution of B's day-2 flag — but identically in the base world and the `do(C)` world, because C's arrow contributes nothing on day 2 in either. The base-versus-branch difference stays exactly zero; I ran the repro here and got the coordinator's numbers.

## How I made it deterministic across machines

- Every block sorted by its own lines; no set ever iterated; no mapping iterated unsorted.
- Nothing about the run is written down: no date, no host, no package version.
- **Full precision stops at six decimal places.** numpy's `exp`/`log` are accurate to well under one unit in the last place but are not promised identical on Linux/Intel (CI) and macOS/Arm (here). Six places is four orders finer than anything shown and ten coarser than those machines can disagree by. Sixteen digits would fail the build for a reason nobody changed — and would promise a reader a seventeenth digit that does not exist, which is exactly what `README.md` was doing.
- **Measured:** four runs — twice plain, once `PYTHONHASHSEED=7919`, once `PYTHONHASHSEED=0` — byte-identical by `cmp`; three more after the final edits, still identical. The suite's test runs the program as a subprocess under `PYTHONHASHSEED=7919` with both API keys stripped.
- I could not test Linux/x86-64 directly (Docker here is arm64; qemu would exercise different SIMD paths than CI anyway), so the six-place rounding is the guarantee rather than a hope.
