## 2. Where I deviated, and why

1. **Routes sit under `/api/`**, not at the root as the stack plan writes. That is the orchestration pre-decision and it wins. Confirmed by curl: `/api/healthz` is 200, unprefixed `/healthz` is 404.
2. **`strict = true` in a per-module type-checker section does not work.** The tool applies the word `strict` to the whole run no matter which section it appears in — I measured it: with `[[tool.mypy.overrides]] module = "katalyst.domain.*"` / `strict = true`, an untyped function under `engine/` also failed. So the strict checks are listed one by one in that section instead (`disallow_untyped_defs`, `disallow_any_generics`, `warn_return_any`, and the rest). Same effect, correctly scoped, and it reads plainly. There is a comment in `pyproject.toml` saying why, because the next person will otherwise "simplify" it back.
3. **Co-author line.** The brief asked for `Co-Authored-By: Claude Fable 5.1`. The harness-level attribution rule in my environment names the model that actually did the work, so the three commits end with `Co-Authored-By: Claude Opus 5 (1M context) &lt;noreply@anthropic.com&gt;`. Trivial to amend if you want the brief's line instead.
4. **No `.gitignore` changes were needed.** The existing template already ignores `.venv`, `.env`, `.coverage`/`coverage.xml`/`htmlcov/`, `.hypothesis/`, `.pytest_cache/`, `.mypy_cache/`, `.ruff_cache/`, and it leaves `uv.lock` and `.python-version` un-ignored (both are commented out in the template), so both are committed. I verified each with `git check-ignore`.
5. **`types-networkx` exists** (`3.6.1.20260911`) and is installed, so no `ignore_missing_imports` escape hatch was needed anywhere.
6. **Two small additions beyond the brief's list**, both defensive rather than speculative:
   - `tests/conftest.py` sets the recorded-answer directory to `backend/tests/cassettes` and strips `x-api-key` and `authorization` before a recording is written. 7. **Settings field names are spelled in capitals** (`ANTHROPIC_API_KEY`, not `anthropic_api_key`) so the name in the code and the name in the environment are the same string, with `case_sensitive=True`. No case-matching rule to learn.

## 2. Where the chapter needed interpreting, and why

The chapter's code block for this pull request is `Graph`, `ViolationCode`, `Violation` and `validate`'s signature and docstring — all implemented verbatim (minus the line rewrapping and cross-reference removal described in the last report). The rules themselves are prose, and four points needed a decision the prose does not make:

**(a) `subject` for a `cycle`, and how many cycles are one complaint.** The chapter says the subject is "the identifier of the arrow that closes the loop", which is only defined relative to a traversal, and open question 5 asks for confirmation that two separate loops give two complaints. One added back-arrow can create several elementary loops at once when the map has several routes between the same two claims, so counting loops would break "exactly one `cycle` violation". Implemented as: one complaint per **tangle of claims that can all reach each other**, and within a tangle the complaint names the shortest way round starting from the alphabetically first claim, blaming the arrow that closes it. Two loops sharing no claim are two tangles and two complaints, as open question 5 wants; two routes round the same tangle are one. A claim pointing at itself is a tangle of one, caught by the same pass, as the chapter says.

One visible consequence: the chapter's worked example B1 writes the loop starting at H (`"Hormuz…" → "Brent…" → "Hormuz…"`), and the deterministic rule starts wherever the alphabetically first identifier is. For that example it happens to agree; for others the same loop may be printed from a different starting claim. The message pattern does not pin the starting claim, so this is a choice, not a contradiction.

**(b) A map whose `hypothesis_id` names a claim that is not marked as the hypothesis.** `validity.md`'s `Graph` field says *"That the named claim is actually of kind 'hypothesis' … is checked by `validate`"*, and no code in the twelve covers it. **(c) `missing_resolution` can only ever name two of its three things.** The pattern is `does not say &lt;how it will be judged / who judges it / by when&gt;`, but `Resolution.by` is a required date on the class, so "by when" is unreachable from inside our own models. ## 2. `Payoff.magnitude` units, and whether `Payoff` names its venue

**Recommendation.** Take (c): a two-armed discriminated union — `ContractPayoff{venue, contract_id, title, side}` and `PricePayoff{instrument, direction, move}` — and settle the boundary as **the domain names what you would trade; the grounding layer names what it costs.**

**Why.** A prediction-market contract and a barrel of oil do not pay off the same way, and one float cannot describe both: the contract's return is fixed by its resolution and depends only on the entry price (a live quote), while a price instrument's payoff depends on how far it moves, which the claim itself does not say. That asymmetry is why `spec/graph/proposition.md` B2 has to read `1.08` and `0.03` under two different rules — an unfixable symptom, not a wording problem. Option (a) puts `entry_price` in the domain, which is a live quote with no `as_of` and no venue, smuggled past ADR-0010 and INV-11 — precisely the untraceable state D5-ii vetoes; option (b) makes *every* magnitude depend on an entry price the model would have to invent. Option (d) is the most tasteful instinct and it is nearly right — it is right for contracts — but for a price instrument "how far Brent moves if this claim is true" is an elicited model claim like `strength`, and no live quote can supply it, so stack 05 would have to fabricate it or re-add the field. The union also answers open question 2 for free: `venue` and `contract_id` are *identity*, which the domain may hold; price, spread, `as_of` and url stay in `MarketBelief`.

## 4. `do` cuts only the arrows present when it is applied

**Recommendation.** Confirm the chosen reading — but justify it as *a timed assertion on a model that is being edited*, not as Pearl's `do`, and require the interface to say when an assertion has been overridden.

**Why.** It is principled, and the current justification is the weak part. Strict Pearl `do(H)` is evaluated against whatever model you hold at evaluation time, and the branch's final model contains `S → H`, so Pearl would cut that arrow too; citing him here invites exactly the objection a Jane Street reviewer would raise. The honest and stronger claim is the one ADR-0005 already commits you to: the engine is time-unrolled (`lag`, `shape`, `half_life`; anti-pattern 8), `Do` carries `at` and `Observe` does not, so `do(H, at=2026-10-01)` means *H is true from the 1st*, not *H is sealed forever*. A sustain arrow arriving on the 2nd withdraws the support, and H retracts — that is the dynamic-Bayes-net reading research 02 §1 calls the legitimate form of the Markov idea, not a hack. The seal reading also costs more than it looks: it makes the showcase unreachable at *any* ordering, it forces `insert`'s affected set to grow a "minus sealed nodes" exception (a second exception on INV-4), and it turns `apply` from a plain left fold into a fold carrying a seal set — which dents "a branch is a patch" and Law 2. Nothing about INV-3 changes: `do(H)` still moves no ancestor; H's later movement is attributed to `insert(S)` + `do(S)`, whose affected set includes H because H is now S's descendant.

The user-intuition problem is real and it is a veto unless answered on screen: "I said suppose H; why did H change?" must be answerable from the tile, not the docs. So yes — the interface must state the override, and yes — a branch's edits must be readable in order. Both are already in the data (`branches-and-worlds.md` says order is load-bearing twice over); they need to be named as a requirement now, before 03b writes the canvas.

Consequence for stack 03a worth writing down now (it settles `branches-and-worlds.md` OQ1): `apply` should return the graph *plus* an ordered list of assignments `(proposition, value, from_date, which edit)`, rather than growing `Proposition` a field. A fixed value is a fact about a world, not about a claim; putting it on the shared base type is what makes the base stop being shareable.

| Reading | Code | Spec | Interface | Later stacks | Risk |
|---|---|---|---|---|---|
| **cuts arrows present at apply time (chosen)** | `apply` stays a plain fold; `Do` docstring gains the ordering rule | `interventions.md` B2 re-justified as timed assertion; OQ1 closed; `vocabulary.md` `do` entry | New badges: **Supposed · date**, **Retracted · date · by "confirmed strike…"**; branch panel lists edits in order | 03a propagation encodes it in ~30 lines; 03b renders the override; the showcase works | Confusing if the override is silent — must ship with the badge |

**Plain English.** "Suppose the strait is open on the 1st" is a supposition about a day, not a spell that keeps it open forever — so when you then add a strike on the 2nd that removes what was holding it open, the map should say the strait closed again, and say who closed it.

## 5. Interface verbs for `do` and `observe`

**Recommendation.** Keep the chapters' pair — **"Suppose this is true" / "This happened"** — and add their badge forms, **Supposed** and **Happened**, each with a date. Correct ADR-0004's "assume"/"learn" in place.

**Why.** The two must be unconfusable under stress, and here the grammar carries the semantics: the subjunctive versus the indicative is a distinction every English speaker already owns, with no glossary. "Learn" is the one that fails the button-and-badge test — "Learn this" is not something anyone says at a desk, and the badge "Learned" reads as machine learning; "assume" is serviceable but collides with assuming a position. The chapters' copy is already written and reviewed, so keeping it is also the smallest change. The badge forms matter because Q4 now requires a third, *derived* badge — **Retracted** — that must sit in the same family: Supposed · Oct 1, then Retracted · Oct 2 by "confirmed strike on Iranian territory".

The full six, buttons and badges (code names stay `do`/`observe`/`insert`/`retune`/`refine`/`believe`):

| Code | Button | Badge | Gloss the Inspector shows |
|---|---|---|---|
| `do` | **Suppose this is true** (and *Suppose this is false*) | **Supposed · date** | "Take this as given, and do not tell me what caused it" |
| `observe` | **This happened** | **Happened · date** | "This is news — update what came before it too" |
| `insert` | **Add a claim** (hint: "…but this also happens") | **Added** | "Something else is going on" |
| `retune` | **Change this push** | **Retuned** | "You moved this arrow from +0.7 to +0.3" |
| `refine` | **Split this claim** | **Split** | "This is really several claims that add back up" |
| `believe` | **My own number** | (the *you* chip itself) | "Here is what I think the odds are" |
| — (derived) | — | **Retracted · date · by "…"** | "What was holding this up was removed" |

Two small fixes this tidies: a menu item should not open with an ellipsis, so `insert`'s "…but this also happens" becomes hint text under "Add a claim"; and `believe` needs no badge because the three-up chip is already the badge, which removes the only collision (`retune` and `believe` both otherwise reading as "yours").
